## Secuencia segura

1. **Preparar y congelar el origen.** Confirmar que no haya importación en curso; hacer backup verificable de D1/R2 y PostgreSQL. Anotar hora, hashes y estado de servicios. Los backups deben completar restauración aislada. Mantener originales R2 hasta finalizar el periodo de reversión.
2. **Sincronizar cambios posteriores al snapshot.** Exportar D1/R2 en una ventana coordinada y repetir la importación idempotente. Transferir evidencia R2 con `npm run migration:transfer-legacy-r2 -- --apply`; comparar conteos, bytes y SHA-256. Mantener D1/R2 intacto. Los alias de cuenta y la atribución de movimientos deben tener soporte confirmado; no inferir una cuenta solo por titular o instrumento.
3. **Validar lectura completa.** Recalcular la cartera desde PostgreSQL y compararla con la autoridad legacy con el mismo corte temporal y las mismas reglas de efectivo. Revisar cantidad, valores, movimientos, lotes de adquisición, renta fija, vencimientos, evidencia y estados de revisión. Cada diferencia debe tener resolución documentada o ser un aviso aceptado explícitamente; no aceptar el corte solo porque el total agregado coincida.
4. **Migrar los caminos de escritura.** La UI, importadores y chat deben escribir en PostgreSQL mediante APIs idempotentes. La API debe soportar crear/revisar/aplicar/rechazar propuestas, auditoría append-only, selección explícita de cuenta de custodia, actualización/publicación de portfolio después de aplicar un evento y errores de concurrencia/idempotencia. Las proyecciones deben leer la versión publicada. Durante el corte debe existir un solo escritor: no dual-write a D1 y PostgreSQL.
5. **Ensayar corte y reversión.** En una ventana operativa, detener nuevas escrituras, capturar un último delta, importar y validar; verificar backup restaurable y una reversión ensayada. Cambiar juntos el backend de lectura y el de escritura. Hacer smoke tests de dashboard, posiciones, renta fija, carga de archivos, captura de evidencia y flujo de propuesta. Si falla una prueba, pausar escrituras y volver a la autoridad anterior usando el delta conciliado; jamás volver a aceptar escrituras en D1 y PostgreSQL en paralelo.
6. **Reabrir y vigilar.** Reabrir escrituras solo después de las comprobaciones. Vigilar errores, duplicados, retraso de ingesta, freshness de cartera/mercado y backup/restore. Al terminar el periodo acordado, retirar la escritura legacy; conservar los originales de evidencia según la política de retención.

## Gates que siguen bloqueando el corte

El corte no está listo porque la aplicación PostgreSQL aún no ofrece una sustitución de extremo a extremo para las escrituras y lecturas financieras de la web actual. La API sombra tiene rutas idempotentes para listar, crear, rechazar y aprobar propuestas. La aprobación agrega el evento y reconstruye/publica la cartera dentro de la misma transacción, siempre que la versión actual tenga una ejecución de origen verificable; si no, rechaza con `PORTFOLIO_REBUILD_REQUIRED`. Las migraciones 026/027 requieren evidencia escrita o foto almacenada, pendiente y del mismo titular; la consumen una sola vez y guardan su referencia en propuesta, auditoría y evento. La migración 028 permite abrir una posición mediante compra aprobada, con evidencia de evento; ventas sin saldo verificado permanecen bloqueadas. El gateway del repositorio incorpora rutas aisladas `/api/shadow/proposals` y `/api/shadow/proposals/{id}/approve|reject`; deriva el actor desde su configuración autenticada, conserva la clave de idempotencia y deja intactas las rutas D1. El gateway y la captura están desplegados en el entorno local privado; el dashboard y los flujos existentes siguen en D1/R2, y el chat PostgreSQL continúa guardando evidencia manual. El actor autenticado configurado (`juanca-family`) tiene rol `reviewer`: puede preparar borradores pendientes sin alterar el patrimonio, pero solo `owner` o `approver` pueden aprobarlos o descartarlos. La decisión final permanece bloqueada para este actor hasta definir y documentar quién puede aprobar movimientos. El smoke test activo previo comprobó catálogo (10 cuentas identificadas y 18 pendientes), listado vacío, rechazo de una cuenta/titular inconsistente sin insertar y rechazo de aprobación falsificando el actor. No se debe ampliar el rol automáticamente. Un cambio de autoridad ahora dejaría vistas obsoletas o movimientos sin registrar.

El gate de compras con posición nueva ya está implementado en la sombra: una compra aprobada con cuenta conocida y evidencia manual crea el evento y una posición verificada cuyo saldo inicial referencia ese evento. La reconstrucción permite esa primera compra incluso si todavía no hay snapshot de esa cuenta. Las ventas sin saldo verificado siguen bloqueadas. La migración `028_event_backed_opening_holdings.sql` agrega la referencia y la verificación de evidencia al esquema; una prueba PostgreSQL cubre compra, creación de posición y publicación.

Pendientes para levantar el gate general: validar movimientos retroactivos reales mediante conciliación de extractos/snapshots; completar el flujo financiero de extremo a extremo desde la UI activa (la pestaña sombra ya compara cartera, ofrece la proyección de renta fija y prepara propuestas/evidencia; dashboard principal, importaciones y revisiones financieras todavía siguen en D1/R2); migrar/reconciliar un delta D1/R2 tomado en la ventana de corte; verificar backups de ambas autoridades para ese mismo delta; ensayar corte y reversión con un solo escritor. Las pruebas sintéticas ya cubren contrato HTTP, idempotencia, atribución/cuenta y ventas concurrentes. El usuario autenticado en la UI mantiene rol `reviewer`, por lo que crear borradores funciona y la aprobación/rechazo requiere un actor `owner` o `approver`; no se cambiará esa autorización por inferencia.

La aprobación ahora rechaza `EVENT_AT_OR_BEFORE_SNAPSHOT` si la fecha efectiva es igual o anterior a la fecha base más reciente de esa cuenta y moneda. La propuesta queda pendiente, sin evento, holdings ni revisión de hechos; se requiere esperar/conciliar el snapshot siguiente. Una prueba PostgreSQL cubre este conflicto y verifica que no haya efectos parciales. Esto cierra la regla automática del motor; los movimientos B3 reales retroactivos siguen siendo un asunto de conciliación con evidencia.
